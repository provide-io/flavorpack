  For a pre-release system where you explicitly said "make sure that 'backward compatible' or 'migratory' logic is not implemented", the Rust implementation's cleaner, more reliable approach is clearly superior for developer experience.

> what about the name/extract_to purpose?

⏺ Looking at the name and extract_to fields in the slot configuration, there's a fundamental design issue with how both launchers handle file extraction:

  The Problem

  The current approach requires awkward workarounds:

  {
    "name": "scripts/simple_test.sh",  // Has to include directory path
    "path": "{workenv}/scripts/simple_test.sh",
    "extract_to": "{workenv}"  // Extract to parent, hoping name preserves structure
  }

  This creates confusion because:
  1. name serves dual purpose - both as an identifier AND as the extraction path
  2. extract_to is misleading - it's not really where the file ends up
  3. Inconsistent behavior - Go launcher seems to ignore directory structure in names

  Better Design Options

  Option 1: Explicit Target Path

  {
    "name": "simple_test.sh",  // Just the identifier
    "source": "{workenv}/scripts/simple_test.sh",
    "target": "{workenv}/scripts/simple_test.sh"  // Explicit destination
  }

  Option 2: Separate Extract Path

  {
    "name": "simple_test.sh",
    "path": "{workenv}/scripts/simple_test.sh",
    "extract_as": "scripts/simple_test.sh",  // Relative to extract_to
    "extract_to": "{workenv}"
  }

  Option 3: Auto-preserve Structure

  {
    "name": "simple_test.sh",
    "path": "{workenv}/scripts/simple_test.sh",
