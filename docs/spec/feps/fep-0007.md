# FEP-0007: Security Model Specification

**Status**: Draft  
**Type**: Standards Track  
**Created**: 2025-01-08  

## 1. Introduction

This specification defines the security model for PSPF/2025 packages, including Ed25519 digital signatures, multi-layer integrity verification, trust chain management, and cryptographic requirements for secure package distribution.

### 1.1. Requirements Language

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

### 1.2. Design Goals

1. Provide cryptographic integrity verification for all package components
2. Support digital signatures with Ed25519 for authenticity
3. Enable trust chain validation for package publishers
4. Define clear security boundaries and threat models
5. Support both secure and development/insecure modes

## 2. Threat Model

### 2.1. Threats Addressed

**Package Tampering:**
- Modification of package contents during distribution
- Injection of malicious code into packages
- Replacement of legitimate packages with malicious ones

**Supply Chain Attacks:**
- Compromised package repositories
- Man-in-the-middle attacks during download
- Compromised build systems

**Integrity Violations:**
- Data corruption during storage or transmission
- Partial package downloads
- File system corruption

### 2.2. Security Boundaries

```
Trust Boundary 1: Package Creation
├── Build System (TRUSTED)
├── Signing Keys (TRUSTED)
└── Package Builder (TRUSTED)

Trust Boundary 2: Package Distribution  
├── Package Repository (SEMI-TRUSTED)
├── Content Delivery Network (SEMI-TRUSTED)
└── Network Transport (UNTRUSTED)

Trust Boundary 3: Package Execution
├── Package Launcher (TRUSTED)
├── Package Contents (UNTRUSTED until verified)
└── Execution Environment (TRUSTED)
```

### 2.3. Out of Scope

This specification does NOT address:
- Runtime code execution security (sandboxing, permissions)
- Network security during package download
- Host system security (antivirus, host intrusion detection)
- Physical security of signing keys

## 3. Digital Signatures

### 3.1. Signature Algorithm

PSPF packages MUST use Ed25519 digital signatures:

- **Algorithm**: Ed25519 (RFC 8032)
- **Key Size**: 32 bytes (256 bits)
- **Signature Size**: 64 bytes (512 bits)
- **Security Level**: ~128-bit equivalent

### 3.2. Key Management

**Key Generation:**
```bash
# Generate Ed25519 key pair
openssl genpkey -algorithm Ed25519 -out private_key.pem
openssl pkey -in private_key.pem -pubout -out public_key.pem
```

**Key Storage:**
- Private keys MUST be stored securely (HSM, encrypted files)
- Public keys MUST be embedded in package index block
- Key identifiers SHOULD use SHA-256 hash of public key

**Key Rotation:**
- Keys SHOULD be rotated annually
- Old signatures remain valid during transition period
- New packages MUST use current signing key

### 3.3. Signature Creation

**Signing Process:**
```
1. Calculate metadata checksum (SHA-256)
2. Calculate each slot checksum (Adler-32)
3. Create signature payload: metadata_hash + slot_checksums
4. Sign payload with Ed25519 private key
5. Store signature in index block
```

**Implementation:**
```python
def sign_package(private_key: bytes, metadata: bytes, slots: list[SlotEntry]) -> bytes:
    """Sign package with Ed25519."""
    import nacl.signing
    
    # Create signature payload
    metadata_hash = hashlib.sha256(metadata).digest()
    slot_checksums = b''.join(struct.pack('<I', slot.checksum) for slot in slots)
    payload = metadata_hash + slot_checksums
    
    # Sign with Ed25519
    signing_key = nacl.signing.SigningKey(private_key)
    signature = signing_key.sign(payload).signature
    
    return signature
```

### 3.4. Signature Verification

**Verification Process:**
```
1. Extract public key and signature from index
2. Recreate signature payload from package contents
3. Verify signature using Ed25519 algorithm
4. Validate all individual checksums
5. Accept package only if all verifications pass
```

**Implementation:**
```python
def verify_package(public_key: bytes, signature: bytes, metadata: bytes, 
                   slots: list[SlotEntry]) -> bool:
    """Verify package signature."""
    import nacl.signing
    
    try:
        # Recreate signature payload
        metadata_hash = hashlib.sha256(metadata).digest()
        slot_checksums = b''.join(struct.pack('<I', slot.checksum) for slot in slots)
        payload = metadata_hash + slot_checksums
        
        # Verify signature
        verify_key = nacl.signing.VerifyKey(public_key)
        verify_key.verify(payload, signature)
        
        # Verify individual slot checksums
        for slot in slots:
            if not verify_slot_checksum(slot):
                return False
        
        return True
    except Exception:
        return False
```

## 4. Multi-Layer Integrity Verification

### 4.1. Checksum Hierarchy

PSPF uses multiple checksum layers:

```
Package Level
├── Index Checksum (Adler-32 of 8192-byte index)
├── Metadata Checksum (SHA-256 of JSON metadata)
├── Signature (Ed25519 of metadata + slot checksums)
└── Slot Level
    ├── Slot Checksum (Adler-32 of stored slot data)
    └── Content Verification (application-level)
```

### 4.2. Checksum Algorithms

**Adler-32 (Fast Integrity):**
- Used for: Index block, slot data
- Properties: Fast, good error detection for small data
- Implementation: RFC 1950 specification

**SHA-256 (Cryptographic Integrity):**
- Used for: Metadata, critical components
- Properties: Cryptographically secure, collision resistant
- Implementation: FIPS 180-4 specification

**Ed25519 (Authentication):**
- Used for: Package authenticity
- Properties: Unforgeable signatures, non-repudiation
- Implementation: RFC 8032 specification

### 4.3. Verification Order

Verification MUST proceed in strict order:

```
1. Magic Trailer Validation
   ├── Check 📦 emoji at start
   ├── Check 🪄 emoji at end
   └── Validate 8192-byte index size

2. Index Block Validation
   ├── Verify index checksum (Adler-32)
   ├── Validate format version
   └── Check structural consistency

3. Metadata Validation
   ├── Verify metadata checksum (SHA-256)
   ├── Validate JSON structure
   └── Check metadata consistency

4. Signature Validation
   ├── Verify Ed25519 signature
   ├── Validate against public key
   └── Confirm payload integrity

5. Slot Validation
   ├── Verify each slot checksum (Adler-32)
   ├── Validate slot table consistency
   └── Check operation chain integrity
```

## 5. Trust Chain Management

### 5.1. Trust Levels

PSPF supports hierarchical trust:

```
Trust Level 4: Root CA Signed
├── Verified by certificate authority
├── Strong identity verification
└── Highest trust level

Trust Level 3: Organization Signed  
├── Signed by known organization
├── Intermediate trust level
└── Suitable for enterprise deployment

Trust Level 2: Self-Signed
├── Package signed by publisher
├── No external verification
└── Requires manual trust decision

Trust Level 1: Unsigned
├── No digital signature present  
├── Integrity only (checksums)
└── Development/testing only

Trust Level 0: Invalid
├── Failed signature verification
├── Corrupted package
└── MUST NOT execute
```

### 5.3. Trust Store Management

**System Trust Store:**
- Location: `/etc/pspf/trusted_keys/` or equivalent
- Format: PEM-encoded Ed25519 public keys
- Management: System administrator controlled

- Location: `~/.pspf/trusted_keys/` or equivalent

- Community verification systems

## 6. Security Modes

### 6.1. Secure Mode (Default)

In secure mode, the system:
- MUST verify all signatures before execution
- MUST reject packages with invalid signatures
- MUST validate complete checksum chain
- SHOULD check certificate expiration
- SHOULD warn about unknown publishers

### 6.2. Development Mode

In development mode, the system:
- MAY accept unsigned packages with warning
- MUST still verify checksums for integrity
- SHOULD log all security decisions
- MUST display clear security warnings

**Activation:**
```bash
export PSPF_INSECURE=1  # Enable development mode
pspf run unsigned_package.psp  # Runs with warning
```

### 6.3. Offline Mode

For air-gapped environments:
- Uses pre-distributed trust store
- No certificate revocation checking
- Relies on signature timestamps
- May accept expired certificates

## 7. Implementation Requirements

### 7.1. Signature Verification Performance

Implementations MUST meet performance targets:

```
Operation                 Target Performance
-----------------------   -------------------
Ed25519 verification     < 1ms per signature
Adler-32 checksum        > 1 GB/s throughput
SHA-256 hashing          > 500 MB/s throughput
Full package verification < 10ms + (size/100MB/s)
```

### 7.2. Cryptographic Libraries

**Approved Libraries:**

Python:
- `nacl` (PyNaCl) for Ed25519
- `hashlib` for SHA-256
- `zlib` for Adler-32

Go:
- `golang.org/x/crypto/ed25519` for signatures
- `crypto/sha256` for hashing
- `hash/adler32` for checksums

Rust:
- `ed25519-dalek` for Ed25519
- `sha2` for SHA-256
- Built-in Adler-32 implementation

### 7.3. Side-Channel Resistance

Implementations SHOULD use constant-time operations:

```python
def constant_time_compare(a: bytes, b: bytes) -> bool:
    """Compare bytes in constant time."""
    if len(a) != len(b):
        return False
    
    result = 0
    for x, y in zip(a, b):
        result |= x ^ y
    
    return result == 0
```

## 9. Security Best Practices

### 9.1. Key Management

**For Publishers:**
- Generate keys on secure, offline systems
- Use hardware security modules (HSMs) for production keys
- Implement proper key rotation schedules
- Maintain secure key backup procedures

**For Consumers:**
- Verify package signatures before execution
- Keep trust stores updated
- Monitor security advisories
- Use automated verification in CI/CD pipelines

### 9.2. Package Distribution

**Repository Security:**
- Use HTTPS for all package downloads
- Implement package signature verification at upload
- Maintain audit logs of all package operations
- Regular security scanning of stored packages

**Content Delivery:**
- Enable integrity checking at CDN level
- Use certificate pinning where possible
- Implement rate limiting and abuse detection
- Monitor for suspicious download patterns

### 9.3. Incident Response

**Compromise Response:**
1. Immediately revoke compromised keys
2. Generate new key pairs
3. Re-sign all affected packages
4. Update trust stores and revocation lists
5. Notify all users of the security incident
