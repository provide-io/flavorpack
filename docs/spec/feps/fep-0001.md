# FEP-0001: PSPF/2025 Core Format Specification

**Status**: Draft  
**Type**: Standards Track  
**Created**: 2025-01-08  

## 1. Introduction

This specification defines the Progressive Secure Package Format (PSPF/2025) core binary layout, including the magic trailer, index block structure, slot table organization, and archive operation chain system.

### 1.1. Requirements Language

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

### 1.2. Design Goals

1. Enable composable archive operations (TAR→GZIP→AES chains)
2. Support cross-language binary compatibility (Python/Go/Rust)
3. Provide efficient 64-bit packed operation encoding
4. Enable memory-mapped access for large packages
5. Support 255 extensible operation types

## 2. Package Structure

### 2.1. File Layout

A PSPF package consists of:

```
Offset       Size        Component
-----------  ----------  -----------
0            Variable    Native launcher binary
N            Variable    Slot data (compressed/encrypted)
EOF-8200     8200        Magic trailer (📦 + index + 🪄)
```

### 2.2. Magic Trailer

The magic trailer is exactly 8200 bytes at the end of the file:

```
Offset  Size  Content
------  ----  -------
0       4     📦 emoji (0xF0 0x9F 0x93 0xA6)
4       8192  Index block
8196    4     🪄 emoji (0xF0 0x9F 0xAA 0x84)
```

### 2.3. Index Block Structure

The 8192-byte index block contains:

```
Offset  Size  Field                Description
------  ----  ------------------   -----------
0       4     format_version       0x20250001 (PSPF/2025 v1)
4       4     index_checksum       Adler-32 of index block
8       8     package_size         Total file size in bytes
16      8     launcher_size        Native launcher size
24      8     metadata_offset      Offset to JSON metadata
32      8     metadata_size        Size of metadata
40      8     slot_table_offset    Offset to slot table
48      8     slot_table_size      Size of slot table
56      4     slot_count           Number of slots
60      4     flags                Package flags
64      32    public_key           Ed25519 public key
96      32    metadata_checksum    SHA-256 of metadata
128     512   integrity_signature  Ed25519 signature
640     7552  reserved             Future expansion
```

## 3. Archive Operation System

### 3.1. Operation Categories

Operations are 8-bit values organized in categories:

```
Range       Category      Description                 Count
----------  ------------  -------------------------   -----
0x00        NONE          No operation                1
0x01-0x0F   BUNDLE        Combine files (TAR, ZIP)   15
0x10-0x2F   COMPRESS      Reduce size (GZIP, ZSTD)   32
0x30-0x3F   ENCRYPT       Secure data (AES, ChaCha)  16
0x40-0x4F   ENCODE        Transform (Base64, Hex)    16
0x50-0x5F   ZIP_VARIANTS  ZIP with specific methods   16
0x60-0x6F   COMPOUND      Other compound formats      16
0x70-0x7F   RESERVED      Future use                  16
0x80-0xFF   USER_DEFINED  Custom operations           128
```

### 3.2. Standard Operations

Core operations MUST be supported:

```
Value  Name              Description
-----  ----------------  -----------
0x01   BUNDLE_TAR        POSIX TAR archive
0x02   BUNDLE_ZIP        ZIP archive container
0x11   COMPRESS_GZIP     GZIP compression
0x12   COMPRESS_BZIP2    BZIP2 compression
0x14   COMPRESS_ZSTD     Zstandard compression
0x30   ENCRYPT_AES256    AES-256-GCM encryption
0x31   ENCRYPT_CHACHA20  ChaCha20-Poly1305 encryption
```

### 3.3. Operation Chains

Operations can be chained in 64-bit packed format:

```
Bit Range   Purpose
---------   -------
0-7         Operation 1 (first applied)
8-15        Operation 2
16-23       Operation 3
24-31       Operation 4
32-39       Operation 5
40-47       Operation 6
48-55       Operation 7
56-63       Operation 8 (last applied)
```

**Example chains:**
- `0x0000000000000111` = GZIP only
- `0x0000000000001101` = TAR then GZIP  
- `0x0000000030111101` = TAR then GZIP then AES256

### 3.4. Chain Processing

Operations MUST be processed left-to-right during creation and right-to-left during extraction:

**Creation:** `data → TAR → GZIP → AES → stored`
**Extraction:** `stored → AES⁻¹ → GZIP⁻¹ → TAR⁻¹ → data`

## 4. Slot Descriptor Format

### 4.1. Slot Table

The slot table contains an array of 64-byte slot descriptors:

### 4.2. Slot Descriptor Layout

Each slot descriptor is exactly 64 bytes:

```
Offset  Size  Field            Description
------  ----  ---------------  -----------
0       8     id               Slot identifier
8       8     name_hash        Hash of slot name
16      8     offset           File offset to slot data
24      8     size             Size of stored data
32      8     original_size    Uncompressed size
40      8     operations       Packed operation chain
48      4     checksum         Adler-32 of stored data
52      1     purpose          Purpose enum (0-3)
53      1     lifecycle        Lifecycle enum (0-15)
54      1     access_hint      Access pattern hint
55      1     priority         Cache priority
56      2     permissions      Unix-style permissions
58      2     platform         Platform hint
60      4     reserved         Future use
```

### 4.3. Purpose Types

```
Value  Name      Description
-----  --------  -----------
0      DATA      General data files
1      CODE      Executable code
2      CONFIG    Configuration files
3      MEDIA     Media/assets
```

### 4.4. Lifecycle Types

```
Value  Name        Description
-----  ----------  -----------
0      INIT        First run only
1      STARTUP     Every startup
2      RUNTIME     During execution (default)
3      SHUTDOWN    Cleanup phase
4      CACHE       Performance cache
5      TEMPORARY   Current session
6      LAZY        On-demand loading
7      EAGER       Immediate loading
8      DEV         Development mode
9      CONFIG      User-configurable
10     PLATFORM    Platform-specific
```

## 5. Package Metadata

### 5.1. Metadata Format

Package metadata MUST be valid JSON containing:

```json
{
  "name": "package-name",
  "version": "1.0.0", 
  "format_version": "2025.1",
  "slots": [
    {
      "id": 0,
      "name": "main-app",
      "source": "app/",
      "target": ".",
      "operations": 273,
      "purpose": "code",
      "lifecycle": "runtime"
    }
  ],
  "execution": {
    "command": "python",
    "args": ["-m", "myapp"]
  }
}
```

### 5.2. Operations Field

The `operations` field contains the packed 64-bit operation chain as a decimal integer.

## 6. Integrity and Security

### 6.1. Checksums

- **Index checksum**: Adler-32 of entire index block with checksum field set to 0
- **Metadata checksum**: SHA-256 of JSON metadata bytes
- **Slot checksum**: Adler-32 of stored slot data (after operations applied)

### 6.2. Digital Signatures

Packages MAY be signed using Ed25519:
- Public key stored in index block (32 bytes)
- Signature covers metadata hash and slot checksums
- Verification MUST occur before slot extraction

## 7. Implementation Requirements

### 7.1. Minimum Implementation

A conforming PSPF reader MUST:
- Parse magic trailer and index block
- Verify checksums and signatures
- Support operations: NONE, BUNDLE_TAR, COMPRESS_GZIP
- Extract slots according to lifecycle rules

### 7.2. Full Implementation

A complete PSPF implementation SHOULD:
- Support all standard operations (0x01-0x31)
- Handle 8-operation chains
- Provide extensibility for user-defined operations
- Optimize for memory-mapped access

## 8. Cross-Language Compatibility

### 8.1. Binary Layout

All integers MUST use little-endian byte order.
All strings MUST use UTF-8 encoding.

### 8.2. Implementation Languages

This specification enables native implementations in:
- Python (via generated attrs classes)
- Go (via generated structs)  
- Rust (via generated structs)

See FEP-0003 for wire format details.
